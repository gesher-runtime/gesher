# 0012 — The framework, headless

**Status:** accepted, 2026-10-22

## Context
Phase 2 ends when an app's `Activity` goes through its lifecycle with its
resources and manifest loaded. That needs Android's framework
(`frameworks/base`): `framework.jar` on the boot class path, its resources
(`framework-res.apk`), and the part of `libandroid_runtime` that the
lifecycle touches. On a device an app is started by `system_server` over
Binder, through `ActivityThread`.

AOSP already runs the framework off-device in two places, and both shape
this decision:
- **Ravenwood** (`frameworks/base/ravenwood`) runs framework code on a host
  JVM for tests. `RavenwoodAppDriver` and `RavenwoodActivityDriver` create
  an `ActivityThread`, a `LoadedApk`, the app's `ContextImpl` and its
  `Application`, then drive an `Activity` through `attach`,
  `performCreate`, `performStart` and `performResume`, without
  `system_server`. System services are in-process stand-ins
  (`RavenwoodSystemServer`).
- **The host `libandroid_runtime`** (`core/jni/Android.bp`, `target.host`),
  which layoutlib and Ravenwood load into a JVM, registers the framework's
  natives without a device: `AssetManager`, `ApkAssets`, `XmlBlock`,
  `StringBlock`, `Log`, `SystemProperties`, `SystemClock`, input events,
  and on Linux `MessageQueue`, `Parcel` and `Binder` (`host_linux`).

Gesher differs from both in having Android's own runtime and libcore, so
the framework runs as it does on a device; Ravenwood's bytecode rewriting
(hoststubgen) and its fake libcore are not needed.

## Decision
- **`framework.jar` is built from source** at the same tag as libcore,
  with javac and D8, as the boot class path is
  ([0007](0007-boot-class-path.md)): no prebuilt Android jars. The sources
  are `framework-minus-apex`'s (`framework-non-updatable-sources`). Code
  generated by Soong is generated by the tools Soong uses:
  - `framework-res`'s `R` and `Manifest` by **aapt2**, which also builds
    `framework-res.apk` with the flags of `core/res/Android.bp`;
  - AIDL interfaces by **aidl**;
  - protos by **protoc** (lite Java) and `protoc-gen-javastream`;
  - aconfig flags by `tools/gen/aconfig_java.py`;
  - event log tags and statslog by small generators in `tools/gen`.

  aapt2 and aidl are taken, like D8, as pinned tools from Google
  (`build-tools` r36.1, Android 16's); protoc from the protobuf release
  that `external/protobuf` pins. They are build tools only and are not
  shipped.
- **Mainline modules the framework compiles against** (Wi-Fi, Bluetooth,
  AppSearch, permissions, ...) are built from their framework sources when
  the headless lifecycle needs them, and from their API stubs otherwise;
  each one is listed in the build with what it is.
- **The framework's natives are linked in**, as libcore's are
  ([0011](0011-libcore-natives.md)): `libandroid_runtime` from the file
  list of its host variant, with `libandroidfw` (resources), `libutils`
  and `libcutils` in full, registered with `dlopen` as
  `libandroid_runtime.so`. `MessageQueue`'s `Looper` needs `epoll` and
  `eventfd`, which gesher-base implements over its file descriptors
  ([0009](0009-socket-fds.md)). Graphics (`libhwui`, Skia) stay out until
  phase 3; their natives are listed as not ported, as libcore's are.
- **Binder in-process.** `libbinder`'s local objects (`BBinder`,
  `Parcel`) work without the kernel driver; the services an app looks up
  through `ServiceManager` are in-process stand-ins, as in Ravenwood,
  starting with the ones the lifecycle calls (activity, package, window,
  display). No `system_server` yet.
- **An app driver.** `gesher-app <app.apk>` reads the manifest and
  resources with `ApkAssets`, loads the dex with a `PathClassLoader`,
  creates the app's `Application` and its launcher `Activity` the way
  `RavenwoodActivityDriver` does, and drives the lifecycle on a main
  `Looper`.

## Consequences
- The framework's build is the largest part of the phase: thousands of
  sources and their generated code, from many AOSP projects (`aosp.lock`
  grows by sparse sets of `frameworks/native`, `system/tools/aidl`'s AIDL
  files, `hardware/interfaces`, `packages/modules/*`, ...). It is done in
  steps that each compile more of it, measured in CI.
- `ActivityThread`'s real path (`bindApplication`,
  `handleLaunchActivity`) is the goal once the stand-in services answer
  enough of it; the driver then becomes a small `system_server`.
- Windows windows, drawing and input are phase 3.
