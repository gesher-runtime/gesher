# Matching NV12 to RGBA delivery: source and complete-path evidence

This is a measured component leaf for issue #56 / T12, with relevant M03/T09/C06
camera and ImageReader integration coverage. It does not complete those broad
roadmap rows or establish a device, Windows, application or release-budget pass.
The raw measurements, original pilot, build identities, failures and independent
review receipts are in [the accompanying JSON](nv12-rgba-2026-11-23.json).

## Scope and observable contract

The existing `Nv12ToRgba` converter performs nearest-neighbor coordinate division
and repeats three chroma expressions for every output pixel. For positive, even,
matching source/destination dimensions, one NV12 chroma pair belongs to a 2×2
luma block. The new guarded path computes those same integer chroma terms once
and writes the four pixels into their existing rows. It preserves destination
stride, exact fixed BT.601 limited-range coefficients, rounding, clamping and
opaque alpha. The original scalar scaling/odd/empty fallback remains verbatim.
The production change is confined to this converter.

This rearranges work on the actual supplied frame. It introduces no allocation,
cache, retained state, replacement input, fabricated camera capability, or
permission exception. The existing reader/window dispatch, status propagation,
callback, queue ownership and image lifetime remain in their production paths.
Synthetic JNI, window and frame sources exist only in explicit test fixtures.
Scope review against `AGENTS.md` and `CONTRIBUTING.md`: compliant for this narrow
transformation, with the platform acceptance limits below still open.

Reference boundaries:

- [Microsoft's NV12 layout](https://learn.microsoft.com/en-us/windows/win32/medfound/recommended-8-bit-yuv-formats-for-video-rendering#nv12)
  describes the Y plane followed by interleaved U/V samples. This change preserves
  Gesher's existing fixed matrix; it does not add generalized color-space support.
- [Android ImageReader](https://developer.android.com/reference/android/media/ImageReader)
  defines queued acquisition, the simultaneous `maxImages` limit and release
  requirements. Public Images and their plane buffers are not used after reader
  close in the new real-ART fixture.
- [Android Image.Plane](https://developer.android.com/reference/android/media/Image.Plane)
  exposes direct storage with row and pixel strides. The integration fixture
  reads each pixel using those reported strides and tests writable independence.

## Measurement boundary and retained results

The final campaign ran **14:48:37.809680–14:49:13.398575 UTC on 23 November 2026**,
with the other three implementation agents explicitly idle for CPU-intensive
work. Six ABBA blocks cover ten workloads, rotating case order by block. Each
invocation is a fresh process with a first single-frame phase and a steady
multi-frame phase: **240 processes, 480 observations**, twelve observations per
variant/case/phase. No sample was excluded. The original one-block pilot remains
as a separate 40-process / 80-observation campaign.

The timed boundary includes native reader/window creation, actual
`CameraFrames_deliver`, the declared JNI-array/window adapters, conversion,
actual queue/enqueue and acquisition, complete pixel/metadata comparison, every
image release, and owner close/destruction. The window case includes geometry,
lock, post, padded-buffer and guard comparisons, and reference retirement.
Two producer buffers alternate. Input generation and independent oracle
preparation occur before timing. The first phase is therefore a first delivery
on a fresh native owner, not whole-process or whole-application cold start.

Timing uses ordinary allocators, with replacement allocators and observer hooks
compiled out, GCC 14.2.0 `-O2`, and strict warnings. Sanitizers and mutations run
separately. CPU uses `CLOCK_PROCESS_CPUTIME_ID`; elapsed time uses
`CLOCK_MONOTONIC`. Every receipt checks exact output signatures, checksums,
assertion counts, source and executable hashes, exit status and owner retirement.
The independent reviewer recomputed all 3,964 evidence checks, including every
median, range, nearest-rank p95 and delta from original process output.

### Adverse observations and limits

The odd-target first-delivery CPU median increases **58.049 µs / 24.57%** and
wall median increases **57.7805 µs / 24.29%**. Its steady CPU median increases
0.5850 µs / 0.34%. The empty-control steady CPU increases approximately
**8.836 ns / 12.99%**, and downscaling increases 0.6911 µs / 1.58%. These controls
do not select the new 2×2 path. The observations are retained without asserting
a scheduler/compiler cause, statistical significance, or an accepted budget.

The smaller pilot also had adverse results: first 2×2 CPU +12.74%, first 720p
+12.19%, steady downscaling +6.38%, and first/steady odd-target +24.42%/+16.51%.
Its unchanged original receipts remain. The larger campaign was predeclared at
six blocks; the candidate was not adjusted to discard negative observations.
With twelve samples per group, nearest-rank p95 is the maximum, not a stable
tail-latency qualification.

There is no claim of allocation/RSS reduction, physical-device throughput,
GPU/IPC/ART performance, Windows/UCRT speed, power saving, or a universal latency
win. Native owner lifecycle and output verification are included; physical
capture, media-framework delivery and application scheduling are not. Actual
Windows and translated-guest CI, device/application evidence and T12 budget
acceptance remain required.

## Correctness and ownership

Both the unchanged baseline and candidate pass **16,777,545 ASan/UBSan checks**.
One actual queued 4096×4096 frame contains every **16,777,216 Y/U/V triple**;
a coverage bitmap verifies each combination occurs, and every RGBA pixel is
compared with independently expanded 64-bit arithmetic and explicit floor
division. The oracle does not copy the implementation's signed-shift expression.

Additional actual production-path checks cover single-axis/tiny/scaled/odd
targets, padded and deliberately unaligned window storage, byte guards, input
immutability, metadata, independent writable image snapshots, `maxImages`,
bounded pending FIFO, producer reuse, separate release, callback reentry and
callback-side close. A deterministic allocation barrier closes the reader while
conversion is in progress; the production closed-owner guard must reject
publication. Callback exceptions preserve the existing native status and pending
Java exception. Window geometry, lock and post failures retain their exact error
and reference/pin retirement. Existing JPEG and internal I420/PRIVATE branches
are regression controls, not new public format-capability claims.

Five compiled mutations must fail their exact intended assertion:

| Mutation | Required rejection |
| --- | --- |
| Use U in the red chroma expression | Complete RGBA oracle differs |
| Reuse the wrong luma row | Complete RGBA oracle differs |
| Replace padded stride with width | Padded-window pixel/guard oracle differs |
| Remove the blue rounding offset | Complete RGBA oracle differs |
| Ignore closed-owner publication guard | Racing close publishes an image |

All five pass their rejection checks. An independent agent replayed the full
sanitized candidate and each mutation. Ordinary timing builds separately pass
16,777,542 checks: the deterministic allocation-hook race's three checks are
deliberately compiled out of ordinary timing, not weakened in correctness CI.
The initial fixture mistakenly expected codec-wrapper callback-exception
translation in the camera dispatcher. Reading the actual unchanged camera path
corrected that fixture expectation; the original failed log is retained, with
no production change for the fixture.

The new `CameraNv12RgbaTest` runs actual Java/ART, JNI and ImageReader APIs in
mandatory Windows track94. It covers ten complete color/scaling cases and
timestamps including zero, real reported strides, direct/writable storage,
independent held images, source-array reuse, release order, bounded pending FIFO
and `maxImages`. All images and buffers stay within their valid reader lifetime.
The gate requires zero exit and all three success markers with a 60-second
deadline. It adds coverage without removing an existing invocation or assertion.
The complete application and services Java/D8 builds pass against the actual
framework and Android core classes; actual Windows execution is still pending.

Both complete baseline and candidate `camera_frames.cc` translation units compile
for Windows x64 under the project's strict C++23/LLVM-MinGW warning set, using
the actual pinned AOSP `android-16.0.0_r4` header closure and existing project
patches. Commands and every header/source hash are retained. A native AArch64
header attempt has the already recorded baseline `sysv_abi` limitation; no
stand-in headers, disabled warning, ARM64 compile success, Windows linking or
runtime result is claimed here.

## Reproduction

Use new empty output paths from the repository root:

```sh
python3 tools/test_nv12_rgba.py --sanitize --negative-controls
python3 tools/test_nv12_rgba.py --sanitize \
  --source-ref 98215dd7e798090fb5ab6160490ae78f1793ab3a
python3 tools/test_nv12_rgba.py --timing --build-output /tmp/nv12-candidate
python3 tools/test_nv12_rgba.py --timing \
  --source-ref 98215dd7e798090fb5ab6160490ae78f1793ab3a \
  --build-output /tmp/nv12-baseline
python3 tools/benchmark_nv12_rgba.py --blocks 6 \
  --baseline-build /tmp/nv12-baseline --candidate-build /tmp/nv12-candidate \
  --output /tmp/nv12-complete-abba.json
```

The driver writes receipts before evaluating results, so a failed invocation is
preserved. It refuses changed sources/binaries, nonordinary timing builds,
nonzero exit, unexpected stderr, output mismatch or inconsistent checks. Local
ptrace restrictions required `ASAN_OPTIONS=detect_leaks=0` for local sanitizer
execution only; ASan/UBSan stayed active, and the CI invocation does not disable
leak detection.
