# Exact row conversion for same-size odd I420 crops

This change lets a valid I420 picture whose visible crop starts at an odd
horizontal coordinate use the existing row converter when the destination has
the same visible dimensions. Complete conversion/publication/retirement
components use **66.91–91.59% less steady process CPU** for the five measured
eligible sizes. The 720p, 1080p and 4K components improve **91.52%, 91.40% and
91.59%**, respectively, on this AVX2-capable Linux host boundary.

Those are conditional source-component results. The original scalar path still
handles scaling and overlapping storage; the original even-crop row branch is
byte-for-byte unchanged. A single-pixel first delivery costs **0.665 µs more
CPU (+6.50%)**, the even-crop first delivery costs **123.559 µs more (+2.48%)**,
and the scaled-up steady control costs **2.48% more CPU**. Every observation,
including the earlier prototype's adverse controls, is retained. This does not
establish application, Windows, codec, GPU, power or universal regression-budget
acceptance.

## Why the row path is exact

`VideoFrame` stores Y followed by separate U and V planes, with independent
luma/chroma strides and an inclusive visible crop. The existing decoder code
can receive a nonzero crop from Media Foundation's
[`MF_MT_MINIMUM_DISPLAY_APERTURE`](https://learn.microsoft.com/en-us/windows/win32/medfound/mf-mt-minimum-display-aperture-attribute):
`MfVideoDecoder::SetOutput` reads its integer offsets and `Emit` retains them in
the frame. Android's [MediaCodec crop description](https://developer.android.com/reference/android/media/MediaCodec)
also defines inclusive right and bottom coordinates. These are source/API
references; no actual device's odd aperture was observed in this experiment.

An odd left coordinate begins at the second luma pixel of a shared chroma pair.
The new path converts that one pixel with the existing `PixelToRgba`, then
advances Y by one byte and U/V by one sample. The remaining luma coordinate is
even, so the original `RowToRgba` function receives exactly its existing pair
alignment. A one-pixel row has no remainder call. Each source row still uses
`(crop_top + y) / 2` for chroma, including odd top offsets and odd heights.

The fast path requires matching visible/destination width and height, positive
dimensions, non-overlapping destination rows, and a destination span disjoint
from the entire source allocation. Its bounded unsigned address differences
avoid forming an unchecked end pointer. Source/output aliases and overlapping
destination rows retain the original scalar read/write order. The existing
valid-frame geometry and destination-storage preconditions remain; this is not
a new validation API for malformed frame pointers or strides.

The original 598-byte even-crop branch is restored exactly and returns before
the new predicate. The existing scalar scaling loop also remains unchanged.
There is no chroma interpolation, color approximation or new SIMD kernel: the
existing generic/AVX2 row implementation does the remaining work.

## Correctness and ownership boundary

The host gate compiles the full actual converter as a separate translation
unit. It also executes the complete actual `QueueSurface` and `RenderFrame`
members, using the existing explicitly declared Android object/dispatch and
clock adapter. The adapter substitutes host `shared_ptr` ownership for Android
`RefBase` and makes the protected destructor accessible for that boundary;
disabled performance tracing and the default timestamp clock are explicit.
Timed deliveries use explicit timestamps. This boundary does not execute an
Android runtime, Media Foundation, a codec provider, a GPU or a Windows surface.
Unused provider/metadata declarations do not return fabricated successful data.

The pixel oracle independently uses nonnegative 64-bit numerators and division
by 1024 after clamping, rather than reproducing the implementation's signed
right shifts. The corpus includes all **16,777,216 Y/U/V triples**, widths 1–131,
odd/even horizontal and vertical crops, row tails, independent source strides,
source/output padding, scaled dimensions, zero extents, overlapping output rows
and bounded source/output aliases. Every output byte and unchanged input byte
is checked where applicable.

Actual producer/consumer checks retain prior output across input mutation,
later frame sizes, abandon and surface destruction. They verify published
dimensions, every pixel, timestamps, frame order, scaling mode and callback
visibility. Null, empty-crop and abandoned surfaces retain their existing
statuses without publishing a frame. Concurrent conversions share immutable
input and use independent destinations.

The final GCC ASan/UBSan run passes **56,900 candidate assertions** and
**38,036 unchanged-baseline assertions**. The baseline fails the new work
assertion as expected. Six separately compiled mutations fail their designated
assertions: disabled odd row path, wrong chroma advance, wrong leading luma,
missing tail, missing height equality and missing disjointness guard. Work
counters are confined to generated correctness code, not ordinary production
or timing binaries. An independent reviewer replayed this entire frozen corpus
and all six mutations successfully.

The first test-observer version used direct external TLS counters and failed;
the final observer uses same-translation-unit reset/read accessors. That failed
run and its generated source remain in the archive, without a compiler or
production-bug attribution. Initial sparse-header assembly failures are also
retained separately from successful compilation.

## Complete-component timing

Both ordinary executables use Clang 23.1.3, `-O2`, ordinary allocation, no LTO,
no sanitizer, no work-counter injection and a common caller/surface object.
The measured host reports an Intel Xeon Platinum 8573C and supports AVX2; the
existing Clang row dispatch selects that implementation. Generic correctness is
also exercised by the GCC gate. The CPU model and capability observation are
environment evidence, not a Windows hardware qualification.

Each timed lifecycle includes queue construction, conversion into its actual
buffer, publication, complete output comparison, prior-owner retention,
abandon, surface destruction and the final retained-owner comparison. Input and
the independent expected image are prepared before both clocks. The first
measurement is therefore **first delivery after input/reference preparation**,
not process/application startup. Same-size cases use actual `RenderFrame`;
scaled controls invoke the actual converter and real queue lock/post directly
because `RenderFrame` requests the visible dimensions.

One predeclared final campaign ran with the other three lanes idle, from
**18:09:37.657623 to 18:10:40.045820 UTC**. Six fixed ABBA rounds over all eleven
cases produced **264 fresh processes and 1,056 observations**. Every process
keeps one first measurement and three steady measurements, including their
original stdout, complete workload identities and timestamps. Within an
observation, lifecycle repetitions are fixed by the case. Both variants must
produce identical complete outputs and checksum/work metadata.

## Preserved pilot and resource tradeoffs

The original 44-process, 176-observation pilot used a combined same-size loop.
It improved targeted odd crops but measured the even-720p control at **+16.58%
steady CPU**, scaled-down at **+8.98%**, and the tiny odd case at **+12.77%**.
Its complete data and original generated source are retained, rather than
being relabeled as measurements of the final source.

Inspection found that the prototype added per-row decisions and offset work
to the even path. Exactly one approved source cleanup restored the original
even branch and isolated the odd branch before the fixed final campaign.
That removes the identified extra work, but timing alone does not prove it
was the sole cause of the pilot's control differences. There was no subsequent
source tuning, threshold change or favorable rerun selection.

The change adds no heap allocation or persistent/per-frame scratch array.
Existing output buffers, copying and ownership remain. In the actual ordinary
Clang objects, the converter's code size increases from **915 to 1,490 bytes**;
the existing generic/AVX2 row helper sizes stay unchanged. Both converter
objects reserve 72 bytes with their local stack adjustment, separate from
register saves. These are compiler-object observations, not RSS, hardware stack
commitment, allocation-rate or whole-application memory claims.
