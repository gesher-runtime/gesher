# ARM64 setjmp signal masks (issue 56 N15)

## Contract and implementation

Android Bionic `setjmp` saves the calling thread's signal mask, `_setjmp` does
not, and `sigsetjmp` selects the behavior using its argument. All three
long-jump entry points restore a mask exactly when their buffer saved one.
Zero becomes a return value of one; other values retain their 32-bit `int`
meaning. The ARM64 ABI preserves the callee-saved general and D registers,
the shadow-stack offset, stack and return address. The current x18 shadow-stack
base is retained while its saved low 14 offset bits are restored. Android does
not save or restore FPCR/FPSR through these functions.

The exact Android 16 implementation has a further restriction:
`__bionic_setjmp_cookie_get` aborts when the flag contains any bit other than
bit zero. The AArch64 entry passes the complete x1 value to that helper.
Consequently flags 2, -1 and INT_MIN are not silently normalized to one.
This was confirmed by running the independent Android Bionic reference;
generic POSIX expectations alone would have produced the wrong behavior.

Primary sources, read at the project's `android-16.0.0_r4` baseline:

- [Public types and API contracts](https://android.googlesource.com/platform/bionic/+/android-16.0.0_r4/libc/include/setjmp.h)
- [ARM64 entry points and register layout](https://android.googlesource.com/platform/bionic/+/android-16.0.0_r4/libc/arch-arm64/bionic/setjmp.S)
- [Shadow-stack size and mask](https://android.googlesource.com/platform/bionic/+/android-16.0.0_r4/libc/private/bionic_constants.h)
- [Signal-flag and cookie validation](https://android.googlesource.com/platform/bionic/+/android-16.0.0_r4/libc/bionic/setjmp_cookie.cpp)
- [Public signal-mask filtering](https://android.googlesource.com/platform/bionic/+/android-16.0.0_r4/libc/bionic/sigprocmask.cpp)
- [Reserved signal-mask rules](https://android.googlesource.com/platform/bionic/+/android-16.0.0_r4/libc/platform/bionic/reserved_signals.h)

Previously Gesher bound all save entry points to identical register-only
instructions and ignored the mask argument. The repair emits separate save
entry points and a common restore path. Mask operations go through the same
resolved Bionic `sigprocmask` implementation that ordinary application calls
and signal delivery use. There is no second translator-local mask. Invalid
flags use the shared Bionic `abort` provider, including its signal-handler
behavior. An incomplete standalone host cannot silently succeed at saving a
mask without a provider.

The buffer is caller-owned, with no side registry, heap allocation or retained
resource per jump. Reusing a buffer for `_setjmp` clears the earlier saved-mask
flag. Mask-free saves/restores do not call a host mask service; mask-saving
pairs make one query and one restore. The generated code remains inside the
256-byte public `jmp_buf` bound (`sigjmp_buf` has 264 bytes). The internal
buffer representation remains private; it is not an interchange format for
a different libc's process-specific cookies or pointer encoding.

## Cookie, mangling and checksum

Android 16 also hardens the buffer. `__bionic_setjmp_cookie_get` returns a
per-process random cookie (stored in word 0 with the flag in bit 0); `sigsetjmp`
XORs x19-x30, SP and the saved x18 offset with it before storing them, and
`siglongjmp` calls `__bionic_setjmp_cookie_check`, which aborts with
`setjmp cookie mismatch` when word 0 does not carry this process's cookie.
Gesher does **not** reproduce the cookie or the register mangling: word 0 holds
only the flag and registers are stored in clear. A buffer copied from another
process, or one whose word 0 was overwritten, is therefore not rejected here
as it is on Android, and saved return addresses/stack pointers are readable
in the buffer. This is a known hardening difference; it does not change the
result of any valid save/restore pair.

Gesher does reproduce the checksum: every save stores the XOR of words 0-23
(flag, mask, core and FP registers) in word 24, written after the saved mask,
and every long jump recomputes it before changing the mask or any register.
A mismatch reaches a non-returning host entry that reports
`setjmp checksum mismatch` and takes the shared Bionic `abort` path, as
Android's `__bionic_setjmp_checksum_mismatch` aborts. A corrupted buffer
therefore aborts instead of continuing with damaged state. A stale but intact
buffer (one whose frame has already returned) is not detected, on Android or
here. `tools/test_arm64_sigsetjmp.py` checks the stored checksum for all save
entry points and corrupts words 0, 1, 2, 3, 14, 15, 16, 23 and 24, requiring the
abort with no mask call and no register change; the previous bytecode fails it.

The checksum, and the buffer layout and mask handling described above,
belong to the Dynarmic translator path only, which emits these entry points
for translated guest code on x86-64 hosts. On native Windows on ARM64, guest
code calls the shim's `gesher_bionic_setjmp`, `gesher_bionic__setjmp`,
`gesher_bionic_sigsetjmp` and `gesher_bionic_longjmp` in
`compat/bionic/extra_sys_bionic.cc` instead. Those store x19-x30, SP and
d8-d15 in words 0-20, the save-mask flag at byte 168 and the saved mask in
word 24, with no checksum, x18 shadow-stack offset, flag validation or cookie;
a corrupted buffer is not detected there. The translator tests above do not
exercise that native path.

The jump helpers' diagnostics follow Bionic: an invalid `sigsetjmp` flag is
printed as a signed value (`-1`, not `18446744073709551615`). A missing or
failing mask provider is reported separately with the provider's return code.
If the translator cannot bind or emit the jump entry points it refuses to
initialize instead of registering null entries or branching to address 0.

The initial QEMU reference exposed a separate oracle limitation: requesting
guest signal 64 was already lost before calling `sigsetjmp`, as independently
confirmed with raw `rt_sigprocmask`. The common native corpus therefore uses
public RT signal `SIGRTMIN+5`, above bit 31, for its wide-mask check. It does
not treat QEMU's inability to represent the highest signal as Bionic behavior.
The production-bytecode fixture continues to check signal 64 using real Linux
thread state.

## Reproduction and CI

```sh
python3 -m venv /tmp/gesher-setjmp-test
/tmp/gesher-setjmp-test/bin/pip install unicorn==2.1.4
/tmp/gesher-setjmp-test/bin/python tools/test_arm64_sigsetjmp.py \
  --arm-cc /path/to/ndk/toolchains/llvm/prebuilt/linux-x86_64/bin/aarch64-linux-android29-clang
```

The `--source-ref` option executes the same assertions against an earlier
Git revision. The native Android oracle is `tests/native/bionic_setjmp_reference.c`;
ARM64 builds also link `tests/native/arm64_setjmp_registers.S`. Run its ordinary
mode for valid behavior and run `2`, `-1` or `-2147483648` in separate processes
for invalid-flag termination.
Its separate `--highest-signal` mode requires signal 64 to survive both public
and raw kernel-mask queries before and after a saved-mask jump. It first sets
an empty public mask and records the resulting raw kernel baseline, requiring
signal 64 to be absent. Bionic's reserved-signal filtering keeps its internal
POSIX-timer signal 32 blocked even for that empty public mask. The probe then
requires exactly `baseline | (1ULL << 63)` before the jump and the entire saved
kernel mask after restoration. Use an Android kernel for this endpoint; QEMU
linux-user rejects the prerequisite before the jump, which is reported as a
failure rather than silently skipped.

The ARM64 workflow runs the independent CPU checks. Windows track 47 runs the
public-API corpus and register caller through the real ELF loader, translated
guest library and shared Bionic provider, and requires its success marker.

## Remaining boundaries

Actual Windows/Dynarmic execution and its current-head CI result remain required.
This local validation does not prove Windows signal delivery, Windows process
termination diagnostics or a full Android 16 runtime comparison. This change
also does not introduce non-local unwinding across suspended native/guest
callback frames. A signal handler that returns normally is covered; a handler
that escapes an intervening host frame requires separate translator lifetime
work and validation. No ARM CPU extension, security capability or application
exception is added. N15 and issue 56 remain open until their complete closure
criteria are met.
