The exec track (wip/exec, ADR 0035) is adding ELF executables as processes in parallel; once it is merged into phase4/integration, merge that in and support arm64 executables the same way.

GOAL (roadmap Phase 7): arm64-only apps run on x86-64 Windows. An APK that ships only `lib/arm64-v8a` must load its native libraries, call JNI both ways, use the NDK APIs Gesher already provides (libc/libm/libdl/liblog/libandroid, EGL/GLES, NativeActivity) and run, exactly as an x86_64 APK does today. At least:
- Choose the translator and record it in an ADR (docs/decisions/0047-arm64-translation.md). Candidates, evaluate honestly: AOSP's own Berberis (frameworks/libs/binary_translation at the pinned tag; check which guest arches are actually implemented there: riscv64 is, arm64 may be partial), dynarmic (A64 frontend, x86-64 backend, 0BSD), QEMU's TCG user mode (GPL: check license compatibility with the project license, ADR 0001). The design that fits Gesher: guest arm64 code is translated; every call into a host library (bionic shim, libandroid, EGL/GLES, JNI from/to ART) goes through generated trampolines that marshal AAPCS64 to the host ABI (MS x64, and System V for JNI) and back, as Berberis' "proxy libraries" and Houdini's NativeBridge do. ART's NativeBridge interface (art/runtime/native_bridge, libnativebridge) is the intended hook: the class loader asks NativeBridge for libraries of a foreign ISA.
- ELF loader support for EM_AARCH64 objects and their relocations (compat/elf, additive and careful: shared with NativeActivity/JNI/exec), arm64 TLS, signals inside translated code (SIGSEGV for implicit null checks in guest code is not needed; guest faults must become Android-like crashes, not hangs).
- PackageManager/installer picks `arm64-v8a` when an APK has no x86_64 libs (primaryCpuAbi, nativeLibraryDir), and `Build.SUPPORTED_ABIS` lists arm64-v8a after x86_64 (with ro.dalvik.vm.native.bridge set as Android does).
- Tests in tests/windows/tracks/47-arm64.ps1: a test APK built in CI with the NDK for arm64-v8a only (JNI calls both ways, libc/libm/pthread/TLS, a callback from guest into Java, a GLES NativeActivity reading back pixels like the existing native-libs tests), passing on both runners. Then an arm64-only real app in the e2e job (pick a pinned F-Droid app that ships only arm64-v8a native code, add it to tests/e2e/apps.json).
- Performance: measure and record (docs/arm64.md) the translation overhead on a CPU-bound native test; a cache of translated code is welcome but correctness first.
Your file domain: a new compat/arm64 (or compat/nativebridge) tree, its cmake/aosp wiring (a new cmake/aosp/*.cmake, aosp.lock additions, tools/fetch-aosp.sh sparse patterns additive), a reusable workflow .github/workflows/arm64.yml wired into ci.yml, compat/elf (additive), the ABI selection in com.gesher.server (minimal), tests/windows/tracks/47-arm64.ps1, its test APK sources, the e2e entry, docs/arm64.md, ADR 0047, the Phase 7 roadmap section (add a checklist).
