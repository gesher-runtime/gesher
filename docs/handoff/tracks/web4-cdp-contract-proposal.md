# Web4 listener transport: proposed contract, not an accepted implementation

Source basis: platform experiment `998cdda20a7f1b0eb5b6010e4ec849fe396b8f33`, run 40683759274 attempt 1, reported in `web4-realm-platform-40683759274.md`. Existing WIP production `28328` and its incremental codec/deadline changes remain unqualified. The experiment did not establish a safe CDP-to-WebView2-frame-COM identity mapping. Do not assume one from a URI, a page-provided value, an integer frame identifier or event arrival proximity.

## Candidate: engine-bound CDP transport in both directions

Investigate using CDP for listener messages and replies end to end, rather than receiving via `Frame.WebMessageReceived` and trying to map that COM frame to CDP. `Runtime.addBinding` reports a `bindingCalled` event with execution context ID, and `executionContextCreated` reports the context's origin, unique ID and auxiliary frame identity. CDP's `uniqueContextId` evaluation is designed to avoid accidental cross-process context reuse. WebView2 exposes a session ID with CDP events and a session-specific command API. Sources: https://chromedevtools.github.io/devtools-protocol/v8/Runtime/ and https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2_11 . The actual security meaning and availability of each field in every supported realm and runtime must be proven, not inferred from the probe alone.

The host would key a *live* realm by host generation, target session and engine unique context ID; `(session, numeric context ID)` is only an event lookup while its unique ID is known. Accept a binding call only if a current, nonambiguous default-world context in the same live session is already recorded, the engine origin is understood and matches the listener's AndroidX rules, and actual frame/main identity is established. The page payload may supply data and the requested listener name; it supplies no authority for origin, frame, document or session. Missing, stale, duplicate, reordered or malformed identity is an explicit failure, never the main frame or a trusted origin by default. Require bounded payload and queue sizes; reject unknown target/session kinds. A callback already accepted for an old document retains its old identity and must not be relabelled on navigation start.

Replies would use the same retained session and unique context, with JSON-encoded data, and target only the originating injected object. A target/session/context retirement invalidates the proxy. A protocol failure or uncertain lifecycle is a failed/dropped reply, never a fallback to the top frame or the newest document. The generic `E_INVALIDARG` observed in the probe only establishes an operation was rejected; it does not prove why. The actual AndroidX contract requires a 1:1 proxy-to-injected-object relationship and silently ignores replies after the originating frame navigates or is destroyed: https://developer.android.com/reference/androidx/webkit/JavaScriptReplyProxy .

## Required lifecycle and deadline model

- Create subscriptions before enabling Runtime/Page and installing the binding. Await each CDP completion whose order matters; Microsoft documents that calls may be processed out of order despite ordered dispatch: https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2.calldevtoolsprotocolmethodasync . Establish the default target before navigation. Auto-attach related targets recursively, using actual `Target.attachedToTarget` type/session and frame-tree events; cross-origin alone is not evidence of an OOPIF. CDP documents `waitForDebuggerOnStart` and explicit resume: https://chromedevtools.github.io/devtools-protocol/tot/Target/ .
- A paused target must be resumed or safely failed under a bounded absolute monotonic deadline, including attach, initialization failure, host destruction and late completions. Timer messages are wakeups, not deadline authority. Never wait synchronously on the STA for CDP completion or hold a mutex across callbacks. Existing Web3 query absolute deadlines, bounded pools, generation retirement, detach and teardown remain unchanged. The currently proposed three-second document-registration budget must not be silently reset by overlapping work or extended by late callbacks.
- Retire realm identity on actual context destruction/clear, target detach, frame replacement and host destruction. Investigate same-document navigation, failed/cancelled navigation, redirects, BFCache, OOPIF swaps and renderer crashes: context destruction alone may not coincide with committed document replacement. Establish committed frame/document identity without misattributing old queued messages. Event ordering and ID reuse must be proven per session, including missing/late/duplicate notifications; uncertainty must fail closed.
- Identify the top frame and nested parentage from actual engine frame/target data, not from a guest label. Maintain separate target sessions and invalidate all children on detach. Verify a session's binding setup before releasing paused script execution. The selected experiment observed iframe targets and nested parentage but did not test detach or stale replies across OOPIF replacement.

## Blocking question: object exposure before the first page script

AndroidX requires the listener object to be injected only in frames whose actual origin matches and to exist before the page's own document-start script. Merely checking a document URL or a guest-computed `location.origin` is insufficient for sandbox, inherited and opaque contexts. `Runtime.addBinding` by itself exposes a generic binding, not the required correctly filtered listener object. Before production changes, demonstrate an engine-authoritative, race-free mechanism that both determines the real realm origin and creates the allowed listener object before any guest script runs, including same-process child frames, OOPIF target startup, about:blank/srcdoc and sandbox. If that cannot be shown, record the unsupported behavior and do not claim complete listener conformance or silently grant access. A page-provided token, URL-derived authorization, or blanket disabling of child frames does not resolve this question.

One research candidate is CDP `Debugger.setInstrumentationBreakpoint` with `beforeScriptExecution`, combined with engine context/origin events and session-specific resume; see https://chromedevtools.github.io/devtools-protocol/tot/Debugger/ . `Page.addScriptToEvaluateOnNewDocument` is documented to run before a frame's scripts, but that timing alone does not make a URL-derived origin check authoritative: https://chromedevtools.github.io/devtools-protocol/tot/Page/ . Neither mechanism has been tested here as an origin-gated injection solution. In particular, prove whether the host receives usable context/origin identity before the pause, whether injected bootstrap itself pauses or races, how OOPIF/blank/srcdoc and no-script documents behave, and how to resume safely on timeout, detach, crash or host destruction. Assess debugger contention and the performance/compatibility cost before considering it for production. A breakpoint or debugger pause must never become an unbounded global stall.

The separate early-platform experiment attempts that breakpoint only in a standalone CI host. It associates `Debugger.scriptParsed` and paused call frames with engine context/session data, exposes a test object only for the exact allowed engine-reported origin, and requires each controlled frame's first script to observe exposure or absence and to exercise the object or a rejected direct binding attempt. It retains the prior nine-realm, held-navigation and stale-operation checks. Every pause has a three-second absolute outcome budget and a separately bounded resume attempt; failures remain failures. This experiment is not a proposed production debugger policy and cannot establish no-script-document, BFCache, detach, crash, performance or full AndroidX behavior. No result exists until actual CI and peer review.

## CI evidence and peer gates before adoption

Use actual two-Windows single-process and device contexts with the original 14 Web3 controls unchanged. Exercise positive same-origin sibling and nested deliveries and isolated reply objects, disallowed-origin forged envelopes, sandbox/opaque cases, about:blank/srcdoc inheritance, redirects, explicit/default ports, wildcard rules, held old-page send and reply after replacement, destroyed frame/host/session, OOPIF attach/detach/swap and delayed setup. Assert actual engine-origin/session/context observations and child process completion, not page-supplied IDs or printed source lines. Include bounded early-registration/delayed-completion failure tests and no callback after teardown. Preserve old red and new source/run/attempt provenance, require focused native/Java lifecycle and security peer review, and do not extend findings to hardware UI, complete Web4, full integration or release.
