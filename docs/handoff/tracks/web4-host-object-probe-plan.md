# Proposed WebView2 frame host-object experiment

This is an independent CI-only platform experiment, not a production Web4 design or proof. `ICoreWebView2Frame::AddHostObjectToScriptWithOrigins` is documented to compare the frame's engine origin at access time, whereas top-level `AddHostObjectToScript` has no origin list. The documentation also says an already obtained proxy can remain accessible after removal, and synchronous host-object calls block page script and cannot safely call back into JavaScript. Sources: https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2frame and https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2.addhostobjecttoscript .

Use a standalone WebView2 host on both Windows runners with the repository's pinned SDK/hash, current-source/run/attempt and actual runtime version. Register one distinct native COM-visible test object per observed frame, using the same exact allowed HTTP origin for every frame; frame names and page labels are test correlation only, never authorization. Subscribe recursively to actual child-frame creation, retain native object/frame identities, and record registration and lifecycle failures. A local server serves two same-origin siblings, a nested frame, a distinct host/origin and a sandboxed same-URL frame. The first inline script in each frame actually attempts a synchronous, constant-time host-object call; matching native call logs, per-object identity and page-observed results distinguish permitted calls from denied attempts. A denied case is not accepted merely because the bridge or script was absent: it must show an actual attempted access, a rejection, and zero native accepted calls for that frame.

Use actual navigation events and a held HTTP response to show the old document still active during a pending navigation. Test a retained old proxy after a real same-frame replacement: the native object records whether a call was delivered and rejects it after the experiment's committed-document retirement. The result must distinguish an engine-level rejection from a call reaching the retired native object; neither a page-provided generation nor navigation-start alone is the authority. Verify the new document's distinct native object and actual accepted call. Include a controlled top-level host-object access from two origins to measure the unrestricted main API separately, with no claim that it provides AndroidX origin filtering.

The host callback performs no JavaScript callback and no waits; an overall process deadline and per-phase monotonic deadlines fail closed. If synchronous host access stalls or its callback/retirement cannot be observed in time, the experiment fails; do not extend Web3 deadlines, cancel a running test to hide failure or claim cleanup of unobserved renderer processes. Check actual normal process termination and record early-call order, native identity, source/run/attempt and logs. This experiment cannot by itself prove an origin-gated AndroidX listener object, complete wildcard/custom-scheme/port behavior, all opaque/inherited contexts, production COM/JNI lifetimes, OOPIF detach/BFCache, full Web4, hardware interaction or release readiness. Source peer and a narrowly scoped two-Windows CI run precede any conclusions.
