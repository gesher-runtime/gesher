Each job observed actual CDP context creation and binding calls for main, two same-origin siblings, a nested frame, a cross-origin frame, nested cross-origin frame, sandboxed frame, about:blank and srcdoc. Actual `iframe` target sessions and frame-parent events were required for the selected cross-origin cases, rather than inferred from their URL. The sandbox context reported the literal CDP origin `://`; the selected about:blank and srcdoc contexts reported the main frame's HTTP origin. These are observations on these runtimes, not a general statement that every opaque or inherited origin is identified safely for production.

During a held navigation, the binding call carried the old context's unique identifier. After response release, the replacement used a different unique identifier in the same frame and session, and the old context-destroyed event was observed. The identical expression succeeded in the replacement and its actual binding was observed. Evaluations against the destroyed identifier and an unobserved `0.0` identifier both returned `System.ArgumentException`, HRESULT `0x80070057`; no later binding was observed during the bounded check. A live JavaScript exception containing the word `context` was independently observed and was not classified as a successful rejection. These observations do not establish why WebView2 rejected either operation.

The earlier run `40682378186`, attempt 1, source `cae4f84d0c74f7b0d0f286b87fdc6f411150c954`, remains red on both runners: the same generic argument exception did not meet its narrower context-gone classifier. The successor added the live identical-expression, unobserved-identifier, exception-type/HRESULT and no-later-binding controls; it did not rerun unchanged source.

This is not proof that a CDP execution context can be mapped securely to a WebView2 frame COM object, nor production Web4 or AndroidX conformance. OOPIF detach and stale lifecycle, other opaque/inherited origins, session ordering under races, document-start registration before every frame's script, and production COM/JNI lifetimes remain open. Original Web3 controls, complete Web4 tests, full integration, package/e2e and physical hardware requirements remain separate.
