# Graphics and input (roadmap phase 3)

Goal: a simple Activity drawn in a real Win32 window that responds to clicks,
verified in CI on Windows. Work happens on branch `wip/graphics`.

## Approach

AOSP already builds Skia, hwui, minikin and libandroid_runtime for the host
(layoutlib, Android Studio's preview). Gesher reuses those host variants:

- **Source lists from Android.bp.** `tools/gen/bp_cc.py` reads a module of an
  Android.bp (its `defaults` in the same file, then the chosen `target`s —
  `host,windows` — and `arch: x86_64`) and writes CMake variables;
  `cmake/aosp/bp_cc.cmake` (`gesher_bp_cc`, `gesher_bp_library`,
  `gesher_bp_flags`) turns them into static libraries at configure time.
  `-D` flags become compile definitions (CMake quotes them for the shell).
- **Skia** (`cmake/aosp/skia.cmake`): `libskia`'s Windows variant, CPU raster,
  built with llvm-mingw (hwui uses Skia's C++ API, so it must share the
  Itanium C++ ABI). Its libraries: FreeType, libpng, libjpeg-turbo (without
  its NASM SIMD: `jsimd_none.c`), libwebp (with its AVX2/SSE4.1 halves),
  wuffs, expat, zlib. Left out of the Windows variant: Fontations (Rust;
  FreeType does the same work) and PDF output (needs HarfBuzz's subsetter).
  `SkUserConfig.h` is the Windows one gn_to_bp.py wrote, with the
  Fontations/PDF defines removed (generated into `out/gen/skia`). skcms's
  AVX2/AVX-512 paths are off, as on Android. `compat/hwui/skia_prefix.h`
  undoes gesher-base's `rand()` macro for Skia (it has locals named `rand`).
  Third-party code is built without `-Werror`/warnings and with `-g0`.
- **hwui** (`cmake/aosp/hwui.cmake`): `libhwui`'s host variant (SkiaCpu
  pipeline, `HWUI_NULL_GPU`), with HarfBuzz, minikin, libui-types and
  libhostgraphics (the host ANativeWindow/Surface/BufferQueue). hwui's
  Windows code paths are its non-`__linux__` branches. `compat/hwui` stands in
  for what Soong generates or Gesher does not build: `HWUIProperties.sysprop.h`,
  perfetto's C API (no-op macros), `tracing_perfetto::getPerfettoCategory`,
  `SharedLib` (dlopen of libandroid_runtime.so → the symbol is in the exe).
  Left out: `YuvToJpegEncoder` (libultrahdr), `LayoutlibLoader`.
  `compat/hwui/graphics_runtime.cc` (`register_gesher_graphics`) registers
  hwui's JNI tables in apex/jni_runtime.cpp's order, plus `android.view.Surface`
  (core/jni/android_view_Surface.cpp, host form, and
  platform/host/native_window_jni.cpp), skipping classes not on the class path.
- **JNI ABI**: hwui's tables go through System V thunks like core/jni's:
  frameworks/base patches `0100-graphics-hwui-jni-helpers.patch`
  (graphics_jni_helpers.h: `CRITICAL_JNI_PARAMS` empty and `GESHER_JNI` under
  GESHER) and `0101-graphics-hwui-sysv-jni-tables.patch` (generated by
  `compat/hwui/gen_sysv_patch.py`, which reuses tools/jni-sysv-patch.py;
  45 files, 878 entries).
- **minikin**: frameworks/minikin patch 0001 leaves the Rust hyphenator out
  (no Rust toolchain); the C++ hyphenator reads the same patterns.
- **CI**: `.github/workflows/graphics.yml` (push to wip/graphics on its inputs,
  workflow_dispatch, workflow_call): builds `skia_probe` and uploads it as
  artifact `graphics`, then builds `graphics_all` (every graphics library)
  with `ninja -k 0`, printing the errors; job `probe` runs the probe on
  windows-2022 when the workflow runs on its own. Graphics targets are
  `EXCLUDE_FROM_ALL`, so `ninja -C out` in ci.yml's build job does not build
  them yet. `tests/windows/tracks/30-graphics.ps1` runs skia_probe in
  ci.yml's test job — but ci.yml does not download the `graphics` artifact
  yet (see next steps), so do not run ci on this branch before wiring it.

### Next concrete steps

1. Get `graphics_all` compiling (graphics.yml loop, `gh run view --log-failed`).
2. Link hwui into dalvikvm: `target_link_libraries(dalvikvm PRIVATE gesher_graphics)`
   (or framework_runtime), and in `compat/framework/android_runtime.cc`
   replace the `android_graphics_ColorSpace` and `gesher_hwui_standins` rows by
   one `{"gesher_graphics", "android/graphics/RenderNode", register_gesher_graphics}`.
   Re-purpose `hwui_standins.cc` / `gen_hwui_standins.py` (zero-answer tables
   from a JNI source + SPECIALS) for device-only classes: SurfaceControl
   (core/jni/android_view_SurfaceControl.cpp, table `sSurfaceControlMethods`),
   BLASTBufferQueue (`android_graphics_BLASTBufferQueue.cpp`, `gMethods`).
   Wire graphics into ci.yml: a `graphics` job (`uses: ./.github/workflows/graphics.yml`),
   test job `needs` it and downloads artifact `graphics` into dist. Check that
   gesher-app lifecycle.apk still reaches onResume with the real natives.
3. Window (design worked out, not written):
   - Native (compat/hwui): `GesherWindow` (one thread per HWND, DIB-section
     BGRA back buffer, mutex, WM_PAINT and WM_PRINTCLIENT blit it so
     `PrintWindow` works off-screen; WM_GETMINMAXINFO allows large sizes;
     per-monitor DPI aware; mouse/key messages queued, an eventfd signals them);
     `Win32Surface : android::Surface` (hostgraphics) overriding
     lock (back buffer, format 5 = BGRA_8888, so Skia draws BGRA)/unlockAndPost
     (InvalidateRect)/query/perform/dequeueBuffer (`reserved[0]` = pixels, for
     SkiaCpuPipeline) and setting ANativeWindow's queueBuffer hook (present).
   - Stand-in natives: SurfaceControl nativeCreate/Copy/finalizer/
     Transaction create+finalizer (NativeAllocationRegistry rejects 0);
     BLASTBufferQueue nativeCreate/Update/GetSurface (Java Surface over the
     Win32Surface via android_view_Surface_createFromSurface)/IsSameSurfaceControl.
   - Java (app/java/com/gesher/app/window, new): an `IWindowSession.Default`
     subclass (addToDisplayAsUser → ADD_OKAY|ADD_FLAG_APP_VISIBLE with frames;
     relayout → fills WindowRelayoutResult frames/config/insets, builds a
     SurfaceControl and attaches the window to it, copyFrom into
     outSurfaceControl), installed by setting `WindowManagerGlobal.sWindowSession`
     by reflection (so StandInServices, the services track's, is not edited);
     `android.app.GesherWindowDriver.show(activity)` doing what
     ActivityThread.handleResumeActivity does (decor INVISIBLE, addView with
     TYPE_BASE_APPLICATION, makeVisible), with
     `inputFeatures |= INPUT_FEATURE_NO_INPUT_CHANNEL` (no InputChannel/
     InputEventReceiver natives needed); focus via `ViewRootImpl.windowFocusChanged`.
   - `SystemProperties.set("debug.choreographer.vsync", "false")` before
     Choreographer is used: no DisplayEventReceiver natives (Ravenwood does the same).
   - Software drawing first (`ThreadedRenderer.disable(false)`), then the
     ThreadedRenderer + SkiaCpuPipeline (its swapBuffers is a no-op: present
     through queueBuffer or a small patch).
   - Main.java: `--window` option; DeviceProfile: make WIDTH/HEIGHT/DENSITY
     non-constant (`Integer.getInteger("gesher.display.width", 1080)`), they are
     inlined today; use e.g. 480x800@160 for the window test.
   - Fonts: Typeface's static init preloads `/system/fonts/Roboto-Regular.ttf`
     and parses the legacy fonts.xml (`SystemFonts.getSystemPreinstalledFontConfigFromLegacyXml`):
     install Roboto + NotoSansHebrew and data/fonts/fonts.xml under $ANDROID_ROOT.
4. CI window test: tests/apps/<window app> (colored Views + Button), run
   gesher-app --window in the background, find the window by title, PrintWindow

5. Input: MotionEvent natives need libinput's Input.cpp (+ InputEventLabels,

6. ANGLE: not started. Plan: a pinned, checksummed prebuilt (libEGL.dll /

   choice in an ADR (0014-graphics-*.md). Building ANGLE from source needs
   depot_tools/gn and a Chromium clang; judged too costly for now.

### Open problems and dead ends

- AOSP android-16 no longer builds libhwui or layoutlib_jni for Windows
  (only Skia keeps a `windows` target); hwui's host (Linux/macOS) variant is
  what is ported.
- libinput in full needs Rust, tflite, flatbuffers and binder AIDL: take only
  the event classes.
- Device-only pieces with no host form: BLASTBufferQueue, SurfaceControl,
  DisplayEventReceiver, InputChannel transport — stand-ins as above.
- framework.yml's host-tools cache key hashes the frameworks/base aosp.lock
  line, which this branch widens: expect one host-tools rebuild.
