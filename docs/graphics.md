# Graphics and input (roadmap phase 3)

Goal: a simple Activity drawn in a real Win32 window that responds to clicks,
verified in CI on Windows. Work happens on branch `wip/graphics`.

## Approach

AOSP already builds Skia, hwui, minikin and libandroid_runtime for the host
(layoutlib, Android Studio's preview). Gesher reuses those host variants:

- **Source lists from Android.bp.** `tools/gen/bp_cc.py` reads a module of an
  Android.bp (its `defaults` in the same file, then the chosen `target`s —
  `host,windows` — and `arch: x86_64`) and writes CMake variables;
  `cmake/aosp/bp_cc.cmake` (`gesher_bp_cc`, `gesher_bp_library`,
  `gesher_bp_flags`) turns them into static libraries at configure time.
  `-D` flags become compile definitions (CMake quotes them for the shell).
- **Skia** (`cmake/aosp/skia.cmake`): `libskia`'s Windows variant, CPU raster,
  built with llvm-mingw (hwui uses Skia's C++ API, so it must share the
  Itanium C++ ABI). Its libraries: FreeType, libpng, libjpeg-turbo (without
  its NASM SIMD: `jsimd_none.c`), libwebp (with its AVX2/SSE4.1 halves),
  wuffs, expat, zlib. Left out of the Windows variant: Fontations (Rust;
  FreeType does the same work) and PDF output (needs HarfBuzz's subsetter).
  `SkUserConfig.h` is the Windows one gn_to_bp.py wrote, with the
  Fontations/PDF defines removed (generated into `out/gen/skia`). skcms's
  AVX2/AVX-512 paths are off, as on Android. `compat/hwui/skia_prefix.h`
  undoes gesher-base's `rand()` macro for Skia (it has locals named `rand`).
  Third-party code is built without `-Werror`/warnings and with `-g0`.
  Ganesh, Skia's GPU backend, with its OpenGL ES half over ANGLE, is built
  too (from the `android` variant's sources; docs/angle.md, ADR 0030).
- **hwui** (`cmake/aosp/hwui.cmake`): `libhwui`'s host variant (SkiaCpu
  pipeline, `HWUI_NULL_GPU`; plus the device's SkiaGL pipeline over ANGLE,
  chosen with `GESHER_HWUI_RENDERER` or `debug.hwui.renderer` = `skiagl`:
  docs/angle.md, ADR 0030), with HarfBuzz, minikin, libui-types and
  libhostgraphics (the host ANativeWindow/Surface/BufferQueue). hwui's
  Windows code paths are its non-`__linux__` branches. `compat/hwui` stands in
  for what Soong generates or Gesher does not build: `HWUIProperties.sysprop.h`,
  perfetto's C API (no-op macros), `tracing_perfetto::getPerfettoCategory`,
  `SharedLib` (dlopen of libandroid_runtime.so → the symbol is in the exe).
  Left out: `YuvToJpegEncoder` (libultrahdr), `LayoutlibLoader`.
  `compat/hwui/graphics_runtime.cc` (`register_gesher_graphics`) registers
  hwui's JNI tables in apex/jni_runtime.cpp's order, plus `android.view.Surface`
  (core/jni/android_view_Surface.cpp, host form, and
  platform/host/native_window_jni.cpp), skipping classes not on the class path.
- **JNI ABI**: hwui's tables go through System V thunks like core/jni's:
  frameworks/base patches `0100-graphics-hwui-jni-helpers.patch`
  (graphics_jni_helpers.h: `CRITICAL_JNI_PARAMS` empty and `GESHER_JNI` under
  GESHER) and `0101-graphics-hwui-sysv-jni-tables.patch` (generated by
  `compat/hwui/gen_sysv_patch.py`, which reuses tools/jni-sysv-patch.py;
  hwui's 45 files and core/jni's `android_view_Surface.cpp`, which is built
  with hwui: its table was missed at first and Surface's natives crashed).
  Gesher's own natives (`window_jni.cc`) are declared `JNICALL` (System V).
- **minikin**: frameworks/minikin patch 0001 leaves the Rust hyphenator out
  (no Rust toolchain); the C++ hyphenator reads the same patterns.
- **In dalvikvm**: `cmake/aosp/graphics.cmake` links `gesher_graphics` (hwui
  and everything under it) into dalvikvm; libandroid_runtime's table
  (`compat/framework/android_runtime.cc`) calls `register_gesher_graphics`
  in place of the Phase 2 stand-ins. Device-only classes (SurfaceControl,
  SurfaceSession, BLASTBufferQueue) get zero-answer tables generated from
  their JNI sources (`compat/framework/gen_device_standins.py`,
  `device_standins.cc`; handles are fresh blocks, finalizers free them).
  Skia's Fontations backend is not built; hwui's host build would use it by
  default, so `compat/hwui/fontations_fallback.cc` gives those calls to
  FreeType. Skia's `kN32` is RGBA (`SK_R32_SHIFT 0`), as on Android.
- **Window** (ADR 0021, `compat/hwui/window`, `cmake/aosp/window.cmake`):
  `gesher::Window` (thread per HWND, BGRA DIB back buffer, `WM_PAINT` and
  `WM_PRINTCLIENT`, `PrintClient`/`ReadBackBuffer`, input queue + eventfd);
  `gesher::Win32Surface` (hostgraphics' `android::Surface` over a window, one
  RGBA buffer presented as BGRA; `lock`/`unlockAndPost`, `dequeueBuffer`
  (`reserved[0]`)/`queueBuffer`, `query`, `perform`); the NDK functions
  (`native_window.cc`); `com.gesher.app.window.NativeWindow` (gesher-app)
  and its natives (`window_jni.cc`).
- **An app's window** (ADR 0029, `app/java/com/gesher/app/window`): the
  window session, `WindowSession` (an `IWindowSession.Stub`), runs in the
  process that draws, as `WindowManagerGlobal`'s session: in gesher-app's
  process (`--single-process --window`) or in an app process the Gesher
  device's system server started (`GesherAppProcess`, the default).
  `addToDisplay` records the window (frames, configuration, insets from
  `WindowLayout` on DeviceProfile's display, 400x800@160 by default) and
  opens its input channel pair; `relayout` creates or resizes its Win32
  window (`NativeWindow`) and hands out a stand-in `SurfaceControl` tagged
  with it, whose `BLASTBufferQueue` gives ViewRootImpl the window's
  `Surface` (`gesher_set_blast_surface_provider`, window_jni.cc). hwui's
  `ThreadedRenderer` draws the views with the CPU pipeline, which dequeues a
  buffer per frame and queues it in `swapBuffers` (frameworks/base patch
  0103), so frames reach the window by themselves; `Win32Surface` presents
  the buffer that was queued (held from dequeue to queue/cancel).
  `finishDrawing` shows the window (or, `--hidden-window`, shows it off the
  desktop: a tool window left of the virtual screen, not activated;
  PrintWindow reads nothing back from a window never shown). The window's
  title is the Activity's label; it carries the process's AppUserModelID
  (`SHGetPropertyStoreForWindow`, from `$GESHER_APP_USER_MODEL_ID`) and the
  package's Start menu icon (`WM_SETICON`, `<data>/gesher-shell`). Closing it
  (`WM_CLOSE`) calls `Activity.finish()`: on the device the system server
  destroys the activity and ends the process; `remove` closes the window.
  Window mode per launch (`--window`, `--hidden-window`, `--headless`,
  `$GESHER_APP_WINDOW`): the launcher tells the system server (`gesher`
  service, `WINDOW_MODE`), which starts the package's processes with it;
  headless processes keep the system server's `StandInWindowSession` and no
  renderer. `GESHER_WINDOW_DEBUG=1` logs the first frames' pixels, the back
  buffer and an in-process PrintWindow.
- **Input in an app's window** (docs/input.md): `addToDisplay` opens the
  window's channel pair; once its Win32 window exists, `attachInput`
  attaches `com.gesher.app.input.WindowInput` to the session's end (initial
  focus: a window shown off the desktop is never activated), so the
  window's mouse, wheel, key, touch and pen messages reach ViewRootImpl's
  `WindowInputEventReceiver`; `closeNativeWindow` closes it before the
  window and the channel go. WindowInput is then the only reader of the
  window's event queue; the rest comes through its listener (on the
  connection's thread, handled on the window's Looper): close (the close
  handler), resize, focus, and WM_CHARs Generic.kcm cannot type (another
  keyboard layout, an IME's text), which reach the focused view as an
  `ACTION_MULTIPLE` KeyEvent (`ViewRootImpl.dispatchInputEvent`; TextView
  inserts it, `KeyListener.onKeyOther`). The window tracks modifier keys
  from its own key messages too (posted messages do not change the thread's
  key state). Services for it: `input` (`VirtualKeyboard.InputManager`:
  the virtual keyboard and Generic.kcm), `content` (TextKeyListener
  observes the text settings; observers are never notified) and a silent
  `audio` (a click plays its sound effect; served by the generated
  `IAudioServiceStub` without StandIn's Proxy, since IAudioService names
  `android.bluetooth.BluetoothDevice`, which framework.jar lacks), in the
  app's process and in the system server.
- **Resizing by the user**: an application window that fills its bounds
  (MATCH_PARENT both ways) is resizable (`WS_THICKFRAME`); its smallest
  client area is the Activity's `<layout android:minWidth/minHeight>`,
  else 220dp (Android's default minimal size of a resizable task),
  enforced in `WM_GETMINMAXINFO`. WM_SIZE becomes the window's bounds:
  `IWindow.resized` gets frames for them and a merged configuration whose
  override has them as `windowConfiguration` bounds and app bounds, as a
  freeform task's (ViewRootImpl lays out from those bounds itself,
  `relayoutWindow`'s local layout, so new frames alone are ignored); the
  views lay out and hwui draws at the new size. The rest of the
  configuration (screen size in dp, density) stays the display's, so the
  Activity is not relaunched. relayout does not resize a window the user
  resizes.
- **Dialogs, menus and other popups** (popups track, ADR 0040): a window that
  belongs to another one is a `WS_POPUP` Win32 window owned by that one's
  (`NativeWindow.createPopup`, `compat/hwui/window/gesher_popup.cc`): no
  taskbar button, kept above its owner, hidden and minimized with it. A
  dialog belongs to its Activity's window, a PopupWindow (menus, a Spinner's
  dropdown, an AutoCompleteTextView's, tooltips) to the window its token
  names, a toast to the app's active window, an Activity with a dialog or
  translucent theme to the window of the Activity below it. It lays out in
  the app window's bounds (sub-windows in their parent's frame, the attached
  frame) and its Win32 window is its surface (the frame and its surface
  insets, room for the shadow; input is offset back), placed in the app
  window's client area and moving with it (`SetPopupBounds`,
  `WM_WINDOWPOSCHANGED`); resizing the app window lays its popups out again.
  A popup whose format has alpha is a layered window (`UpdateLayeredWindow`
  from the CPU pipeline's premultiplied buffer: the dialog's card and shadow
  over the app; opaque with SkiaGL). The session keeps each app window's
  group (`WindowSession.updateGroup`): the app window dimmed by the topmost
  `FLAG_DIM_BEHIND` popup's `dimAmount` (`Window::SetDim`, in its paint), the
  popups raised by Android layer, and input routes (`Window::SetInputRoute`:
  a window's events go to another one's queue, translated through the
  screen): a modal popup gets the pointer events of the windows below it (a
  click outside a dialog cancels it and never reaches the Activity), a gesture
  stays where it started, the topmost focusable window gets the keys,
  `FLAG_WATCH_OUTSIDE_TOUCH` popups a press where one starts outside them.
  Not focusable: `WS_EX_NOACTIVATE`, unfocused; not touchable:
  `WS_EX_TRANSPARENT`. Hidden windows are never activated, so the session
  gives the Android focus (to the topmost focusable window); shown windows
  get it from Windows' activation. Closing a popup (Alt+F4, WM_CLOSE) is Back
  in it; a dialog-themed Activity's window finishes the Activity. Toasts are
  drawn in the app's process (`ToastHost`, the process's `Toast.sService`: a
  text toast as SystemUI's ToastUI shows it, a custom toast's TN, one at a
  time for 2 s or 3.5 s). An Activity started on top of another in its task
  takes the task window's place and size; the window below is hidden when its
  Activity stops and comes back where the task's window is; the title is the
  TaskDescription label when the Activity set one.
- **ANativeWindow for libandroid** (native-libs track): dalvikvm defines, as
  Microsoft-ABI C functions, hostgraphics' `ANativeWindow_acquire/release/
  getWidth/getHeight/getFormat/dequeueBuffer/cancelBuffer/setDequeueTimeout/
  tryAllocateBuffers/getLastDequeue*/getLastQueueDuration` and the
  interceptor setters; libandroid_runtime's `ANativeWindow_fromSurface`;
  and Gesher's `ANativeWindow_lock`, `unlockAndPost`, `setBuffersGeometry`,
  `setBuffersTransform`, `setBuffersDataSpace`, `getBuffersDataSpace`,
  `getBuffersDefaultDataSpace`, `setFrameRate`,
  `setFrameRateWithChangeStrategy`, `ANativeWindow_toSurface`
  (`compat/hwui/window/gesher_native_window.h` lists them; they work on any
  hostgraphics Surface). libandroid binds an Android .so's imports of these
  names to them through its System V thunks; `gesher_window_create(title,
  w, h)` gives a test a window and its ANativeWindow without Java.
- **CI**: `.github/workflows/graphics.yml` (push to wip/graphics on its inputs,
  workflow_dispatch, workflow_call): builds `skia_probe`, `skia_gl_probe`
  (run by 31-angle.ps1, next to ANGLE's DLLs) and `window_probe`
  (`ninja -k 0`) and uploads them as artifact `graphics`, then builds
  `graphics_all` (every graphics library), printing the errors; job `probe`
  runs both probes on windows-2022 when the workflow runs on its own. Graphics
  targets are `EXCLUDE_FROM_ALL`, but dalvikvm links hwui, so ci.yml's
  `build` job builds them too (ccache key `runtime`). ci.yml runs
  graphics.yml as its `graphics` job; the test and package jobs download
  artifact `graphics` into `dist`. framework.yml builds `graphics-tests.dex`
  (`tests/dex-graphics/build.sh`, against framework.jar's classes, with
  gesher-app's sources on javac's source path) into artifact `framework`.
  `tests/windows/tracks/30-graphics.ps1` runs the probes and the dex tests
  (`GraphicsDex`: framework.jar and gesher-app.jar on the boot class path,
  a time limit, fault tracing).
- **libc++ strictness** (`gesher_graphics_cxx` in `cmake/aosp/hwui.cmake`):
  ui_types, hostgraphics and hwui build as C++23 (utils/Trace.h mixes C's
  `<stdatomic.h>` with `<atomic>`) with `<new>` and `<cmath>` force-included
  (StrongPointer.h's `std::nothrow`, ui/Rect.h's `std::round`), and without
  `-Winvalid-specialization`/`-Wdeprecated-declarations` (math/half.h).
  `surface_control_private.h` comes from frameworks/native/include/private;
  `compat/hwui/include-native/hardware/hardware.h` stands in for
  libhardware's header (ui/PixelFormat.h needs only `<system/graphics.h>`).
  frameworks/base patch 0102: PathIterator's `nextHost` calls the
  @CriticalNative `next` without JNIEnv/jclass under GESHER, as on a device.

### Stand-ins and gaps (what is not real yet)

- **Device-only natives** answer zero/null or fresh handles
  (`device_standins.cc`): SurfaceControl (+ Transaction), SurfaceSession,
  BLASTBufferQueue, OverlayProperties, Perfetto's. Handles carry a tag:
  `BLASTBufferQueue.nativeGetSurface` returns the Surface of the window its
  SurfaceControl was tagged with. InputChannel, InputEventReceiver and the
  other input natives are the input track's real ones (docs/input.md).
- **The system server does not know the app's windows** (ADR 0029): no
  server-side window list, focus or z-order; dialogs and popups are
  top-level windows of their own, not owned by or placed relative to their
  parent. No vsync (`debug.choreographer.vsync=false`: frames timed by
  messages).
- **Surface natives missing on the host**: core/jni's host
  `android_view_Surface.cpp` has no `nativeCreateFromSurfaceControl`,
  `nativeGetFromSurfaceControl`, `nativeGetFromBlastBufferQueue`,
  `nativeReadFromParcel`/`nativeWriteToParcel` (`#ifdef __ANDROID__`).
  `Surface.copyFrom(SurfaceControl)` and the BLAST paths that call them
  throw UnsatisfiedLinkError.
- **CPU drawing only**: hwui's CPU pipeline (Skia raster); hwui's GL
  pipeline over ANGLE is not wired up.
- **System fonts** come from the fonts track (docs/fonts.md: fonts.xml in
  `$ANDROID_ROOT/etc`, the font map through SharedMemory); SystemFonts'
  own `/system/etc/fonts.xml` read still fails and logs a stack trace.
- **hwui logs "Using Fontation backend"** (its host default); the calls go
  to FreeType (`fontations_fallback.cc`).
- **Window details**: one buffer per surface; a resize reaches the next
  lock/dequeue. A user resize changes the window's bounds only, not
  `screenWidthDp`/`screenHeightDp` (no configuration change for the app's
  resources, no relaunch); windows that are not full-size application
  windows (dialogs, popups) follow the app's layout and are not resizable.
  A window shown off the desktop (`--hidden-window`) stays off it when
  resized (`WM_WINDOWPOSCHANGING`).
  Per-monitor DPI aware, sizes in pixels, density 160 by default whatever
  the monitor's scaling; CI runs at 96 DPI.
- **Input gaps** (docs/input.md): Generic.kcm is a US layout, so with
  another keyboard layout a key types both its US character (the KeyEvent)
  and the layout's (the WM_CHAR); no IME (InputConnection) path; the
  content service never notifies observers.

### Open problems and dead ends

- AOSP android-16 no longer builds libhwui or layoutlib_jni for Windows
  (only Skia keeps a `windows` target); hwui's host (Linux/macOS) variant is
  what is ported.

  the event classes.
- Device-only pieces with no host form: BLASTBufferQueue, SurfaceControl,
  DisplayEventReceiver, InputChannel transport — stand-ins as above.

  line, which this branch widens: expect one host-tools rebuild.

  stub) are gone; the stand-in generator lives on for device-only classes.
