# Build and package from a defined source

Use this guide with [the native build recipe](../README.md#building),
[framework build](framework-build.md), [boot image](boot-image.md),
[installer behavior](installer.md) and [desktop responsibilities](architecture.md#desktop-script-responsibilities).

## Choose and record the source

Record `git rev-parse HEAD` and `git status --short` before building. Retain the
checkout SHA, workflow run ID and attempt, supplier receipts, assembly ledger,
installer version, checksum and test outcome together. For a PR, GitHub's merge
checkout and API head SHA can differ: `tools/ci/source_identity.py` handles that
distinction. Do not replace either with a guessed branch head.

The authoritative complete build is `.github/workflows/ci.yml`: a main push,
PR run, or manual `workflow_dispatch` on a selected ref. Release tag pushes use
that same pipeline. Running a workflow or publishing is a separate action from
preparing local changes. A dirty local checkout has no corresponding qualified
CI artifact until its changes have gone through that pipeline.

## Existing installer pipeline

The `package` job consumes the committed `tools/ci/package_artifacts.json`:

| Artifact | Producer | Assembly owner |
| --- | --- | --- |
| windows-x64 | build | windows_x64 |
| framework | framework / framework | framework |
| graphics | graphics / build | graphics |
| angle | angle / probe-build | angle |
| arm64 | arm64 / build | arm64 |
| boot-image | boot-image / compile | boot_image |
| media | media / media | media |

In that job, the existing sequence is:

1. Run desktop script checks on Windows.
2. Run `python tools/ci/artifact_receipt.py --batch tools/ci/package_artifacts.json --destination ci-suppliers/package`.
   The destination must be new. This verifies the committed manifest, checkout,
   repository, run/attempt and successful producer identity. It stages the batch,
   revalidates live supplier identity, then publishes the artifacts together.
   This command requires the real Actions context and GitHub API access/token;
   it is not an offline downloader for arbitrary artifacts.
3. For each owner in the table's order, run
   `python tools/surface/assemble-artifacts.py --source ci-suppliers/package/artifacts/OWNER --destination dist --ledger ci-owners.json --owner OWNER`.
   Preserve the order and ownership ledger; do not overlay unrelated files.
4. Run `python tools/web3/host_roles.py verify --dist dist` to reject test-only
   query fixtures in production inputs.
5. Compute the version with `python tools/ci/release_version.py`. Invoke Inno Setup
   6 (including its Hebrew language file) as the workflow does:
   `ISCC.exe /Qp /DBuildDir=ABSOLUTE_DIST /DAppVersion=VERSION /OABSOLUTE_INSTALLER tools/package/gesher.iss`.
   Generate `SHA256SUMS.txt` for the resulting executable.
6. Test that installer in the disposable CI Windows environment: install, verify
   installed metadata/helpers, run actual applications with
   `GESHER_REQUIRE_BOOT_IMAGE=1`, check upgrade/data retention and uninstall.
   Consult the workflow for the complete current checks. Do not run these steps
   against a developer's active installation.

The `gesher-setup` artifact is uploaded before installation tests. Its presence
alone therefore does **not** mean the package job passed. Check the job and e2e
outcomes. `publish-release.yml` separately verifies and publishes the exact
tested installer; do not rebuild a different executable for release.

## Requirements and limits of local rebuilding

Native production compilation requires Linux/WSL and the pinned llvm-mingw
archive/selected pthread overlay described in the README. Framework, graphics,
ANGLE, ARM64, media and boot-image have their own producer recipes in the
workflows; a native-only build is not a complete installer. Windows packaging
requires Inno Setup 6 and Windows/ART integration checks. Dependency sources,
patches and toolchain selections come from the checked-out recipes, not the
contents of an installed Gesher directory.

Without the complete source-bound supplier batch and Actions receipts, local
ISCC output is only an unqualified development package. A version string or
checksum does not establish coherent provenance or compatibility. Do not fill
missing suppliers from an active installation, compile-only artifacts from
another source, or individually rebuilt files. Stop and report the missing
producer or evidence instead. This guide establishes traceable inputs; it does
not claim bit-for-bit reproducibility of all tool outputs.

## Derived outputs

`out*` build trees, `dist`, `ci-suppliers`, `ci-owners.json`, `installer` and
local `outputs/` contain derived material, not new source. Keep installers and
receipts as validation artifacts outside the PR diff. The installed
`gesher-version.ini` is generated by Setup; editing it cannot qualify a build.
The Android profile and user application data are runtime state, never suppliers.
Local coordination notes also stay outside the PR.

## Validate script organization safely

From the repository root, use Windows PowerShell 5.1:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tests/windows/shell/ControlPanelActionChecks.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tests/windows/shell/InstallErrorChecks.ps1
```

These existing tests exercise production worker/native process code and error
propagation with isolated helper fixtures. They cover sequencing, busy/close
policy, Unicode/literal arguments, native stderr, failure paths and handle
cleanup. They do not prove actual Android install, camera, permissions, boot
or application behavior. Full package/e2e jobs supply the Windows/ART evidence.
After extraction, keep the tests pointed at the production module and include
that module explicitly in `gesher.iss`; the package job checks its installed
presence. No active installation needs modification for these local checks.
