[app/README.md](../app/README.md), or simply `gesher-app my.apk
--system-server`, which starts all of them for one run). `gesher-app my.apk`
runs it on the persistent Gesher device instead (0026; `gesher-app status`,
`shutdown`; logs in `%LOCALAPPDATA%\Gesher\logs`, one `<package>.log` per
app). `GESHER_BINDER_TRACE=1` makes binderd trace every transaction on stderr;
`GESHER_APP_METHOD_TRACE=<dir>` (a drive-less path) makes each app process the
device starts stream an ART method trace to `<dir>/<package>-<pid>.trace`,
which survives an abort (it found the HealthConnectManager placeholder's need).

- 1c, the app process: `gesher-app --system-server` runs
  `android.app.GesherAppProcess`: two binder threads, `new ActivityThread()`,
  `attach(false, 0)` (→ `attachApplication`), `Looper.loop()`; a launcher
  thread calls `startActivityAndWait` with the MAIN/LAUNCHER intent (plus

  The system server (`ActivityManagerService`, `ActivityTaskManagerService`,
  `ActivityClientController`; three binder threads besides the main one)
  pairs the process with the start (by the caller's pid), calls
  `bindApplication` (the configuration, an empty `ProviderInfoList`, core
  settings, and the ApplicationSharedMemory region read-only, written with
  the SDK feature versions of no feature and animator scale 1), and on
  `finishAttachApplication` schedules a `ClientTransaction` of
  `LaunchActivityItem` + `ResumeActivityItem`. The framework's
  `handleBindApplication` (LoadedApk's own class loader, the Application,
  the network security config...), `handleLaunchActivity` and
  `handleResumeActivity` (the decor view added through the window session,
  laid out by Choreographer frames) run, and the app reports
  `activityResumed` and `activityIdle`. Finishing (`finishActivity` from
  `Activity.finish()`, or `removeTask`) is `PauseActivityItem`, then on
  `activityPaused` `StopActivityItem`, then on `activityStopped`
  `DestroyActivityItem`; on `activityDestroyed` with no activity left the
  server calls `scheduleExit`, and gesher-app ends (`EXIT_APPLICATION` →
  `Looper.quit()`, which the main Looper refuses: that is the exit).
  `GesherAppDriver` is not used in this mode.

### Open problems, dead ends ruled out
- `access("/dev/binder")` uses the CRT's `_access` (gesher-base has no
  `access` override), so libbinder's `selfIfKernelBinderEnabled` cannot see
  the device; patch 0002 avoids it rather than changing gesher-base's
  `access` (another track's area; roadmap Phase 1 item).
- servicemanager's Looper main (binder fd polling + timerfd) is not used:
  binderd has no poll support. Adding poll would need an asynchronous
  "work available" notification per thread connection.
- `BINDER_TYPE_FD` travels for fds backed by a Windows handle (files,
  memfds, pipes); sockets and eventfds do not (binderd refuses them). fd
  arrays (`BINDER_TYPE_FDA`) are not supported.
- All processes report uid 10000 (gesher-base's getuid), except that the
  system server's binder calls carry 1000 (`GESHER_BINDER_UID`, read by
  `/dev/binder` when the process opens it). Access off-Android reports uid 0
  to ServiceManager, so registrations are allowed; services checking
  `Binder.getCallingUid()` see 10000 for every app. The system server gives
  every package that uid too.
- Natives a reply's Parcelable needs must exist in the receiving process even
  when the value is null (`readTypedObject(Foo.CREATOR)` initializes `Foo`);
  OverlayProperties was the first (now a stand-in).
- framework.jar's classes are Java 21 class files, so building gesher-app
  (StubGen, javac) needs JDK 21; only CI has the framework's classes. (For
  1c the framework job uploaded them once, temporarily, to build gesher-app
  locally and run it against CI's binaries; that step is gone again.)
- Debugging the attach path: `GESHER_APP_TRACE_LOOPER=1` prints each message
  the app's main Looper dispatches; ART's method tracing
  (`dalvik.system.VMDebug.startMethodTracing`) finds where an exception
  without a stack trace (the boot class loader's pre-allocated
  NoClassDefFoundError: a class of a module framework.jar lacks) comes from.
- The window is never drawn: relayout gives no surface and the session no
  input channel. A real `IWindowSession`, the real natives and the fonts
  (`/system/etc/fonts.xml` and `/system/fonts` are paths on the current
  drive, ADR 0010) are the graphics track's.
- Local builds: WinLibs g++ warns (`-Warray-bounds` false positives in
  vector inserts) where clang does not; CI uses llvm-mingw.
