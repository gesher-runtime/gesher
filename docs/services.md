# Binder and system services (Phase 4, services track)

Design: [0015](decisions/0015-services-binder-ipc.md),
[0017](decisions/0017-services-system-server.md). Tests:
`tests/windows/tracks/50-services.ps1` (dot-sourced by `run-tests.ps1`).

## Pieces

| Piece | Where |
|---|---|
| `/dev/binder` in gesher-base (client side of the driver) | `compat/posix/src/binder.cc`, `binder_internal.h`, `binder_wire.h`; hooks in `path.cc` (open, `PathKind::kBinder`), `fd.cc` (close/dup/dup2), `system.cc` (ioctl), `mman.cc` (mmap), `stat.cc`; `posix.cmake` adds bionic's uapi with `-idirafter` |
| binderd, the driver as a process | `compat/binder/binderd.cc` |
| servicemanager | frameworks/native `cmds/servicemanager` (Access.cpp, ServiceManager.cpp) + `compat/binder/servicemanager_main.cc`, `compat/binder/include/selinux/*` stubs; `cmake/aosp/servicemanager.cmake`; `aosp.lock` adds `cmds/servicemanager/` to frameworks/native |
| Probes | `probes/binder/binder_probe.cc` (raw ioctls: server = context manager, client, nested call, objects both ways, death), `probes/binder/libbinder_probe.cc` (libbinder + servicemanager across processes) |
| Java test | `tests/dex-services/gesher/services/BinderTest.java`, built by `tests/dex-services/build.sh` in framework.yml into `services-tests.dex` |
| libbinder → out-of-process servicemanager | `patches/frameworks/native/0002-servicemanager-over-binderd.patch` |
| Java threads for binder pools | `compat/framework/android_runtime.cc`: `androidSetCreateThreadFunc` (attach pooled threads to the VM, as AndroidRuntime's `javaCreateThreadEtc`); `android_os_ServiceManagerNative` registered (`framework.cmake` source added) |
| APK parsing (PackageParser2) | `app/java/com/gesher/server/ApkPackage.java` |
| system_server-lite and the services | `app/java/com/gesher/server/` (`SystemServer`, `Services`, `PackageManagerService`, `WindowManagerService`, `StandIn`); stubs generated by `app/gen/StubGen.java` (run by `app/build.sh`) into `com.gesher.server.stub` |
| gesher-app's multi-process mode | `app/java/com/gesher/app/Main.java` (`--system-server`), `RemoteServices.java`; launcher `tools/package/gesher-app.ps1` (`--system-server`) |

Running by hand: `set GESHER_BINDER=mydev`, start `binderd.exe mydev`, then
`servicemanager.exe`, then any processes using binder (dalvikvm with
framework.jar, or the probes; the system server and gesher-app as in
[app/README.md](../app/README.md), or simply `gesher-app my.apk
--system-server`, which starts all of them). `GESHER_BINDER_TRACE=1` makes binderd trace
every transaction on stderr.

  - `PASS  installer: gesher-app --system-server runs the app with the services in a system server process`
- 1a, APK parsing: `com.gesher.server.ApkPackage` (replacing
  `AppManifest.java`) parses with framework.jar's `PackageParser2`
  (`ParsingPackageUtils`, a callback enabling no compat change, no
  certificates), and generates PackageInfo/ApplicationInfo/ActivityInfo with
  `PackageInfoCommonUtils.generate`, plus what installing adds (source and
  data dirs, uid, `FLAG_INSTALLED`). The launcher Activity comes from the
  parsed MAIN/LAUNCHER intent filters; `queryIntentActivities` matches
  filters with `IntentFilter.match`. It worked at the first run: no native
  or service was missing. The parser adds `android.app.AppDetailsActivity`
  to every package (PackageInfoCommonUtils leaves it out; the log line does
  too). No fallback reader: a parse failure fails the launch.
- 1b, system_server-lite: `com.gesher.server.SystemServer` (in
  gesher-app.jar) parses the APKs it is given, creates the services
  (`Services`, `PackageManagerService`, `WindowManagerService`; the old
  `StandIn*` code, moved from `com.gesher.app`) and registers them with
  servicemanager, then joins the binder thread pool. Each service's Binder
  is a generated `com.gesher.server.stub.IFooStub extends IFoo.Stub`
  delegating every method to the `StandIn` proxy: `app/gen/StubGen.java`
  writes them in `app/build.sh` by reflection over framework.jar's classes
  (on the JDK, with `-XX:-BytecodeVerificationRemote`; Stubs whose interface
  has `@EnforcePermission` methods get a no-op `PermissionEnforcer`, since
  their deprecated `Stub()` asks ActivityThread for the system context).
  The same stubs serve the single-process mode in-process. `gesher-app
  --system-server` waits for `package` in servicemanager, reads the package
  name with `ApkLiteParseUtils`, gets the ApplicationInfo with
  `getApplicationInfo` and the launcher Activity with
  `queryIntentActivities` across processes, and launches; every
  `getService` of the app goes to servicemanager.
- One client-side workaround (`com.gesher.app.RemoteServices`):
  `DisplayManagerGlobal` is created over the remote `display` service with
  `getOverlaySupport` answering null in the app process. Reading that call's
  reply (even a null one) initializes `android.hardware.OverlayProperties`,
  whose static initializer calls `nGetDestructor`, a native of
  libandroid_runtime's `android_hardware_OverlayProperties.cpp` (libgui)
  that Gesher does not register; in-process the stub returned null without
  touching the class. Remove it when those natives land.
- 1d, the launcher: `gesher-app my.apk --system-server`
  (`tools/package/gesher-app.ps1`) starts binderd and servicemanager for a
  device of its own (`gesher-app-<pid>`) and the system server with the APK,
  runs the app, then stops the three; their logs go to
  `%LOCALAPPDATA%\Gesher\logs`. The installer ships `binderd.exe` and
  `servicemanager.exe`. The single-process mode stays the default (the
  `.apk` association uses it).

### Next steps
1. System services (roadmap item 2), incremental, each verified in CI:
   a. Done (above).
   b. Done (above). The services are still stand-ins answering for the
      lifecycle (the stand-in log lists what an app calls beyond them:
      `IDisplayManager.getPreferredWideGamutColorSpaceId`,
      `IActivityManager.checkPermissionForDevice`,
      `IActivityClientController.setTaskDescription` for lifecycle.apk).
   c. The app process via `ActivityThread.attach(false, startSeq)`:
      `IActivityManager.attachApplication` → `bindApplication` → the server
      schedules `ClientTransaction` (`LaunchActivityItem`,
      `ResumeActivityItem`) on `IApplicationThread.scheduleTransaction`, so the
      real `handleBindApplication`/`handleLaunchActivity` path runs and the
      server, not gesher-app, drives the lifecycle. Where it plugs in:
      `Services.ActivityManager` (attachApplication: call
      `thread.bindApplication` with the ApplicationInfo from
      `PackageManagerService`, a null services map and null font map —
      `BINDER_TYPE_FD` is not supported), `Services.ActivityTaskManager`
      (the transactions), and a third mode in `com.gesher.app.Main` that
      calls `ActivityThread.main`-like code instead of `GesherAppDriver`.
      The server will need a second binder thread (it calls into the app
      while the app's main thread may call it): `BinderInternal.setMaxThreads`
      or a `Binder.joinThreadPool` thread. Expect trouble in the real
      `handleBindApplication` (LoadedApk's class loader goes through
      `ClassLoaderFactory`'s native `createClassloaderNamespace`, not
      registered; hwui and ddm setup). Real AMS/ATMS (services.jar) are out
      of reach for now; the server side is Gesher's, the client side the
      framework's.
   d. Done (above).
2. For the graphics track: `window` is
   `com.gesher.server.WindowManagerService`, minimal. A real
   `IWindowSession` plugs in with `WindowManagerService.setSessionFactory`
   (a `Function<IWindowSessionCallback, IWindowSession>`); to be served to
   other processes the session must be an `IWindowSession.Stub` (in-process
   any implementation works). `IWindowManager` methods the window code needs
   go into `WindowManagerService` (an `IWindowManager.Default` subclass;
   the generated stub forwards every method to it).

### Open problems, dead ends ruled out
- `access("/dev/binder")` uses the CRT's `_access` (gesher-base has no
  `access` override), so libbinder's `selfIfKernelBinderEnabled` cannot see
  the device; patch 0002 avoids it rather than changing gesher-base's
  `access` (another track's area; roadmap Phase 1 item).
- servicemanager's Looper main (binder fd polling + timerfd) is not used:
  binderd has no poll support. Adding poll would need an asynchronous
  "work available" notification per thread connection.
- `BINDER_TYPE_FD` is not supported yet; needed once services pass
  ParcelFileDescriptors/SharedMemory (e.g. bindApplication's font map —
  the server can pass null).
- All processes report uid 10000 (gesher-base's getuid). Access off-Android
  reports uid 0 to ServiceManager, so registrations are allowed; system
  services checking `Binder.getCallingUid()` will see 10000 for everyone.
  The system server gives every package that uid too.
- Natives a reply's Parcelable needs must exist in the receiving process even
  when the value is null (`readTypedObject(Foo.CREATOR)` initializes `Foo`);
  OverlayProperties is the first (above).
- framework.jar's classes are Java 21 class files, so building gesher-app
  (StubGen, javac) needs JDK 21; only CI has the framework's classes.
- Local builds: WinLibs g++ warns (`-Warray-bounds` false positives in
  vector inserts) where clang does not; CI uses llvm-mingw.
